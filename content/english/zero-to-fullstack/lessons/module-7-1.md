## 明确目标，清点行囊

清点行囊，现在`zero-to-tech`项目由三样东西组成：

- **静态前端** ，基于 React 和 Next.js 开发，可以构建为静态前端代码
- **FastAPI 后端** ，基于 Python 和 FastAPI开发，通过 Uvicorn 提供服务
- **SQLite**，对应硬盘上的一个.db文件

然而，距离上一次把`zero-to-tech`项目发布到服务器上，已经过去整整十几节课了。现在通过浏览器访问服务器的IP地址，还可以看到它，但那还仅仅是一个静态前端网站。

目前我们已经实现了后端 API、建了数据库、做了会话，只不过全是在本地开发、本地运行的。

在开发后端功能时，前端也有一些调整，比如说我们给它加了`fetch`，让它可以请求后端API，还添加了历史记录列表、会话这些feature。

所以如果要做全栈部署，我们前后端都要做，只不过前端只需要推送代码、重新构建。而后端要从零开始部署。

这就是这一节的起点。

## 如何部署

"部署"说到底是一句话：**把在我们自己电脑上能跑的东西，在另一台机器上（尤其是服务器）跑起来。**

我们这个项目，虽然说是有前端、后端和数据库三部分，但是SQLite数据库基本上就是后端的一部分。因为它的安装、创建、使用都是基于Python的能力。所以我们可以理解为我们要部署的就是前端和后端。

### 朴素的部署方案

服务器部署一般也会叫“线上部署”，或者“上线”，这些基本都是同样的意思。

我们的项目在本地运行的时候，是前端通过`npm run dev`监听3000端口，后端通过`fastapi dev`监听8000端口（背后是Uvicorn）。我们自己可以通过浏览器访问3000端口获取页面，接着页面中的js脚本再通过fetch访问8000端口的后端程序，实现交互。

既然服务器也只是一台电脑，我们可以用一种朴素的方式来思考部署方案：

前端监听服务器的一个端口，后端监听服务器的另一个端口，用户通过浏览器获取前端页面，页面中的js脚本再通过fetch访问后端程序。

只不过前端不需要监听3000端口了，我们前面讲前端的时候一直是用Nginx监听80端口并转发前端资源的（反而在本地监听3000端口只是为了方便开发的“权宜之计”罢了）。所以在这个朴素的部署方案中，前端仍然通过Nginx来代理，通过80端口给到用户。

而**后端则是与本地运行一样的模式，通过Uvicorn的能力，在8000端口提供服务。**

按照这种“朴素的部署方案”，那许多事情对于我们来说，就不是一个全新的知识领域，有不少我们已经知道的东西。但是也存在一些我们要了解的新知识点。
### 我们已经知道的

#### 1. 前端部署流程
关于前端，我们已经知道该如何部署——先把代码推到服务器，然后构建为静态前端代码，交给Nginx就好了。我们在模块 3、4 的时候对此已经轻车熟路，等下我们基本可以按照曾经讲过的前端部署方案来部署。

只不过有一处需要注意——我们在5.5那一节的时候，给前端加了一个配置文件`.env.local`，而这个配置文件并没有被git所追踪，所以等下我们要处理它（先记着账）。

#### 2. Python环境

我们知道电脑上要**有 Python**环境，这是后端运行的基础。在服务器上安装Python并不复杂，Ubuntu自带了Python，如果我们想要其他版本也可以很轻松地安装。我们已经知道如何安装 Python。

#### 3. .venv 和依赖

我们知道要在Python的基础上安装项目依赖，例如 fastapi、uvicorn、pypinyin、snownlp，并且我们用 **`.venv`** 来管理这些依赖。我们此前介绍过 requirements.txt，通过pip install 是可以把依赖都安装回来的。包括venv也是Python官方自带的能力，所以这个问题也不大。我们已经知道如何使用venv，也知道如何通过 requirements.txt 文件来 install 后端依赖。

#### 4.代码和数据库

我们知道项目**代码**要完备，目前我们有`main.py`、`storage.py`，代码运行的时候会自动创建 **`history.db`**。关于拉取代码到服务器，我们已经很熟悉——前端代码是怎么拉到服务器上的，后端代码就如何拉到服务器上，背后是git 和 GitHub 在发挥作用。而关于数据库，如果是 MySQL 或者 PostgreSQL 这样的数据库，部署的时候可能会有一些麻烦，但是我们用的是SQLite，后端代码运行的时候会自动创建的。这也是我们已经知道的。

#### 5.启动后端服务
我们知道需要通过Uvicorn监听一个端口来提供API服务，我们在本地一直是使用`fastapi dev`命令来自动调用Uvicorn，默认监听8000端口。

以上这些都是我们已经知道的。

### 我们会遇到哪些挑战

但是，服务器部署与本地运行毕竟还有显著差异（不然也不会有我们今天这节课了）。如果只凭我们目前已经知道的这些去部署，还会遇到下列的挑战：

#### 挑战 1. 缺失前端配置文件

`.env.local`文件不进git，所以当我们把项目代码pull到服务器上之后，服务器上**没有任何前端配置**。

而且服务器上要的也不是 `.env.local` 这个名字——`.local` 的意思就是"本机私有"，它是给我们自己开发用的。线上构建要的是另一个名字，等下会讲到。总之**前端的配置得在服务器上手动建一份**，不然构建出来的前端不知道该去哪儿找后端。

这属于是配置文件的问题。
#### 挑战 2. 后端配置不匹配

后端代码`main.py`中有一个CORS中间件（`CORSMiddleware`），其中有这样一行代码
```python
allow_origins=["http://localhost:3000"],
```

这行代码在线上运行时候肯定会出问题，因为localhost的意思就是本地。我们的项目部署之后是需要用户通过互联网访问的，这行代码会“水土不服”。

讲道理，这种内容就不应该写在代码里，它应该写进单独的一个配置文件，因此这个和上一个前端问题一样，也属于是配置文件问题。
#### 挑战 3. 仅支持本地访问的`fastapi dev`

本地通过`fastapi dev`来启用`Uvicorn`监听端口没问题，但是它有一个问题在于它只接收本地的访问，也就是发请求的电脑也是运行程序的同一台电脑。按照我们现在的部署逻辑，用户要在自己的电脑上通过js向我们的服务器的8000端口发请求，所以这个方案会行不通。

但好在FastAPI的文档有介绍，如果面向公网提供服务，需要用`fastapi run`命令。用这个命令运行的时候，Uvicorn就不止能够处理来自本地的请求了。
#### 挑战 4. 终端窗口不敢关闭

我们在本地运行`zero-to-tech`项目的时候，前后端分别需要一个终端窗口，窗口关闭服务就停了。部署到服务器之后，前端可以不再依赖持续开着的终端窗口，因为前端的部署方案是构建为静态页面，由Nginx去提供服务。

但是后端就比较尴尬——后端的终端窗口要一直开着，一旦关闭，后端服务就停了。

#### 挑战 5. 防火墙

我们的服务器在云平台上，前端和后端目前分别通过80端口和8000端口监听请求。80端口已经开放了，我们在讲前端的时候就已经确认过这件事。但云平台的**安全组 / 防火墙**默认情况下不会开通8000端口。我们需要手动去给它放行。

---

> 方案定了，会撞上的问题也预判到了，接下来就是一个一个解决。**把五条挑战归拢一下，其实是四件事**：
>
> 1. **处理配置文件**（挑战 1、2）——这件得在**本地**办，上服务器之前就要办完；
> 2. **换成 `fastapi run`**（挑战 3）——一条命令的事；
> 3. **开通防火墙**（挑战 5）——去云平台控制台点一下；
> 4. **让后端在后台常驻**（挑战 4）——等前面都跑通了，最后办。

---
## 配置文件

先办第一件：**挑战 1 和挑战 2**。

这两条看着一个在前端、一个在后端，其实是**同一类问题**——都是"某个值不该写死，它得随着机器变"。而且它们都得**在本地办完再推上去**，所以放在上服务器之前。

### 什么是配置

同一份代码，跑在我们自己的电脑上和跑在服务器上，有些东西就是会不一样，比如说前端 / 后端地址。因为不同的服务器 IP 不同，地址自然也会不同。

除此之外，还有其他的一些信息值得放在配置中，包括：
- 前后端地址
- 数据库地址和连接配置（包括密码）
- 第三方服务密钥（例如大模型 API key）
- 服务监听哪个端口
- 日志写到哪儿、要不要开调试模式

这些可以写在同一个配置文件中，用类似下面这种方式来写：

```bash
名称a=xxx
名称b=123
```

把这些保存为一个文件，代码就可以从中读取到运行所需的参数了。这个文件就叫做配置文件。

**这些东西不属于代码。** 代码回答的是"怎么做"，而配置回答的是"这一次，对着谁做"。

代码和配置之间是相互配合的。同一份代码，如果配上不同的配置，就能服务不同的环境。我们这个项目里，有两处和地址相关的配置。

一处就是前端的`.env.local`文件：

```text
# 前端根目录，.env.local
NEXT_PUBLIC_API_BASE_URL=http://localhost:8000
```

这个文件里写了后端的访问地址，并赋值给一个常量 `NEXT_PUBLIC_API_BASE_URL`，前端在请求后端的时候就会顺着这个常量找到`http://localhost:8000`这个地址。

**另一处在后端**，就是前面提到的这行：

```python
    allow_origins=["http://localhost:3000"],     # 5.5 加的
```

它本不应该写死在代码里，而是应该也抽取为一个配置文件。5.5那一节的时候我们提过这件事，当时说 **“后端这类配置，留到部署那一节一起处理”** 。

**今天就是那一节。** 

### 配置文件的命名、读取

配置文件的命名有一些松散的规矩，基本上会叫做 `.env`，但之所以说松散，是因为有时候也可能不会这么命名，这取决于框架认不认它。

比如说我们现在项目中唯一的一个配置文件，就是前端的`.env.local`

为什么是叫`.env.local`而不是`.env`呢？其实 Next.js 两个都认，但后缀在传递不同的意思：`.local` 表示**本机私有**（即别人机器上没有，也别提交）。

同时 Next.js 还认下面这几种写法：

 - .env.development.local
 - .env.development
 - .env.production

`.production` 表示**生产环境构建时才用**。5.5 那份配置本来就是本机私有的，所以叫 `.env.local`。

> **有余力的话，可以了解一下 Next.js 到底是怎么找配置文件的。**
>
> 它不是"只认一个"，而是**按固定顺序找一串，先找到的值优先**。以 `npm run dev` 为例，顺序是：
>
> ```text
> .env.development.local  →  .env.local  →  .env.development  →  .env
> ```
>
> `npm run build` 时则把中间的 `development` 换成 `production`。
>
> 这个顺序解释了两件事：**其一**，`.env` 也是认的，只是优先级最低，所以适合放"各环境通用"的值；**其二**，`.local` 那几个排在前面，意味着**本机的设置永远盖过公共设置**——这正是"本机私有"该有的待遇。


上述说的是前端 Next.js 的配置文件。但是Python后端的要求就和 Next.js 不同，我们等会儿使用python代码来读取配置文件的时候，它认的就是`.env`，这种情况下就不需要加其它后缀。

有了这些配置文件之后，只需要把它们放在项目的指定位置，在代码中通过约定的方式就可以读取到。比如说前端配置文件就放在前端项目的根目录，而后端配置文件就放在后端项目的根目录（在我们`zero-to-tech`项目中，后端配置文件需要放在 `/backend` 下）

此外，python读取配置文件的时候，需要使用一个 `python-dotenv` 库，等会儿我们要安装一下。

>为什么配置文件名称前面有个点？这是因为点开头的文件是隐藏文件，用隐藏文件写配置也是一种心照不宣的约定。

### 配置文件与git

我们在5.5那一节讲前端配置文件的时候，提到过一个知识点——配置文件不进git

这是因为 git 在很多时候会用来在不同的设备之间同步代码（比如说本地电脑与服务器之间），而配置文件又和具体的设备有关，所以它们不需要同步。

此外还有一个更重要的原因，那就是配置文件中很可能会包含密码、密钥这些信息。这些信息的保密程度显然比代码的保密程度要高，因此 **绝对不能随着代码推送到远程仓库，尤其是GitHub的公开仓库！** 

这种情况下，我们就需要把配置文件写入到`.gitignore`中，明确要求 git 忽略它。

### README与.example

让 git 忽略配置文件是出于安全考虑，但它会引起一个问题——别人拿到代码之后跑不起来，并且不知道需要补充哪些配置，也不知道配置文件应该叫什么名字、按什么格式写配置，就会“玩不转”这个项目。

这怎么办？

按照惯例，所有项目的根目录中，都需要有一个`README.md`文件，我们此前的章节中也多次遇到过这个文件。比如说在GitHub上创建一个新的仓库时有一行 "Initialize this repository with a README"，就是在询问是否需要建一个README文件；我们在判断一个开源的库靠不靠谱的时候也会去看它的README文件。

这个文件的作用就是告诉拿到这份代码的人这个项目是怎么回事，解决什么问题，代码结构是怎么样的，以及如何运行它。

有了README文件，就可以解决配置文件缺失的问题了——可以把配置文件的要求写在README里，人们拿到代码之后照着README中写的去创建配置文件就行了。

但是，关于配置文件，大家还会有一个心照不宣的约定，那就是写一份示例配置文件，叫做example，放在项目中。

比如说，我们项目中依赖一个`.env`配置文件，这个文件不能进 git 代码仓库，那我就创建一个 `.env.example`文件（也有人叫 `.env.sample`、`.env.template`，都是一回事）。

它和 `.env` 长得一模一样，键和名都有，只是**值全是示例**。因为没有真的值，所以就可以进git了。它在代码运行的时候也不会真的生效，它的作用就是给我们去看配置文件应该怎么写。

### 动手处理配置文件

后端配置目前还是写死在代码里，所以我们先处理它。需要干两件事。

1. **把值搬出去**——挪到一个专门放配置的文件里；
2. **让代码去读它**——让程序启动时自己去那个文件里取。

一件一件来。

**第一件：把值搬出去。** 在 `backend/` 下新建一个 `.env` 文件：

```text
# backend/.env
ALLOWED_ORIGINS=http://localhost:3000
```

实际的配置就一行（顶部那行 `#`开头的是注释，不会被代码读取）。

按照前面说的，这个文件不能进 git。打开 `.gitignore` 确认有这一行：

```
.env*
```

没有就现在加上。然后 `git status` 看一眼——**`backend/.env` 不该出现在待提交列表里**。

> 这一步别跳过。"配置不进 git"不能靠"我记得应该被挡住了"，**要靠亲眼看一次 `git status`**。

**第二件：让代码去读它。** 需要改一下后端python代码`main.py`：

在顶部先引入两个库：
```python
import os
from dotenv import load_dotenv
```

紧接着，读取配置文件：
```python
load_dotenv()                        # ← 读同目录下的 .env

ALLOWED_ORIGINS = os.getenv("ALLOWED_ORIGINS").split(",")
```

然后，修改中间件的`allow_origins`的值，不再使用写死的`http://localhost:3000`，而是换成从配置文件中读取出来的动态的值：

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=ALLOWED_ORIGINS,   # ← 不再写死，从配置来
    allow_credentials=True,
    ...
)
```

注意，这个`dotenv`不是python标准库的成员，所以我们需要手动安装一下，并且记录到`requirements.txt`中

```bash
cd backend
source .venv/bin/activate
pip install python-dotenv
pip freeze > requirements.txt        # 老规矩，记账（6.1）
```

> 这个`dotenv`只干一件事：把 `.env` 里的值读进环境变量。

改完之后**本地验证一下。** 后端用`fastapi dev` 跑起来，前端 `npm run dev`，文字实验室照常能用的话，就**说明后端配置文件改好了**。想更确定，把 `.env` 里那行改成一个别的地址、重启后端，再点分析——**这次真被拦了**。再改回来就可以了。

至此，后端配置就单独抽取成一个配置文件了。接下来我们创建前后端配置文件的示例文件。

### 创建配置示例文件

在项目根目录`~/zero-to-tech/`下创建`.env.example`文件：

```text
NEXT_PUBLIC_API_BASE_URL=http(s)://[ip]:[port]
```

在项目的后端根目录 `~/zero-to-tech/backend`下创建`.env.example`文件:

```text
ALLOWED_ORIGINS=http(s)://[ip]:[port]
```

注意**键要写全，值给一个能用的示例，或者写有指引性的内容**——这样别人 `cp .env.example .env` 之后，改值就行，不用再去猜键叫什么。

这样，两个example文件就建好了。

不过这里会有一个问题。我们的配置文件虽然不需要让git追踪，但是这两个.example文件还是要随着代码一起提交的，所以不能被忽略。现在`.gitignore`的写法是`.env*`，会把这两个文件也拒之门外，所以我们需要允许它们被追踪，在`.gitignore`的 `.env*`下面添加一行：

```
!.env.example
```

这样，就把示例配置排除在列表之外了，也就意味着它们可以随着代码提交了。

### 提交代码

到这里，本地的活基本全干完了——代码改了、配置样例建好了。一起推：

```bash
git add -A
git commit -m "CORS 名单改为从配置读取；补 .env.example"
git push
```

### 写配置文件

依赖装完了，下一步是准备配置文件

先写前端的配置文件


```bash
cd ~/zero-to-tech
cp .env.example .env.production
vim .env.production
```

在里面写

```bash
NEXT_PUBLIC_API_BASE_URL=http://服务器ip地址:8000
```

再写后端配置文件

```bash
cd ~/zero-to-tech/backend
cp .env.example .env         # 照抄一份
vim .env                     # 再改值
```

在里面写
```
ALLOWED_ORIGINS=http://服务器ip地址
```

**注意这里没有端口号**，别顺手写成 `:3000`，也不要写`:80`

这两份配置值的变化规律**并不一样**，值得对照着看一眼：

| 配置 | 本地 | 线上 | 变了什么 |
| --- | --- | --- | --- |
| `NEXT_PUBLIC_API_BASE_URL` | `http://localhost:8000` | `http://服务器IP:8000` | 只换了地址 |
| `ALLOWED_ORIGINS` | `http://localhost:3000` | `http://服务器IP` | 地址换了，**端口也没了** |

为什么后端这份连端口都变了？因为 `ALLOWED_ORIGINS` 登记的是"**允许谁来找我**"，也就是**前端页面所在的那个源**。本地的前端跑在 3000 端口上，而线上的前端是 **Nginx 在 80 端口**提供的——80 是 http 的默认端口，浏览器发出的 `Origin` 里根本不带它。

**所以配置值要跟着"那台机器上的事实"走，不能照着本地做字符串替换。** 这也正是配置存在的意义：**同一份代码，在不同机器上适配各自的实际环境。**


后端**正式上线用 `fastapi run`**

```bash

```

启动日志（示意，以你实机为准）：

```text

 server   Server started at http://0.0.0.0:8000
   INFO   Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)
```

可以看到背后仍然是跑了Uvicorn，并且是跑的地址是 `0.0.0.0`，不是`127.0.0.1`，这是 **`run` 和 `dev` 的一个重要区别**：

|         | `fastapi dev`         | `fastapi run`        |
| ------- | --------------------- | -------------------- |
| 改代码自动重启 | **有**                 | **没有**               |
| 默认监听    | `127.0.0.1`——**只听本机** | `0.0.0.0`——**听所有网卡** |

## 服务端的后台运行

只剩最后一条了：**挑战 4**。

网站能用了，很想合上笔记本去睡觉。

**先别急。** 做个实验：**直接关掉 SSH 窗口**。

再刷新网站——页面还在（那是 Nginx 送的静态文件），但点分析按钮，**转圈、报错**。

前端没问题，但后端程序死了！

原因是uvicorn 目前是个**前台进程**，它寄生在我们的 SSH 会话里，我们走了它就没了。

> **"会话"这个词又出现了。** **我们和服务器之间那段连着的关系**就是SSH会话，从登录那一刻开始，到退出那一刻结束。

我们希望uvicorn的运行不依赖会话，我们关掉终端之后它仍然可以持续在服务器上运行。对于这个需求 Linux 有现成的办法。

我们再次通过SSH登录远程服务器，但是这次不再直接执行 `fastapi run`命令，而是这样：

```bash
cd backend
nohup .venv/bin/fastapi run > backend.log 2>&1 &
```

`cd backend` 我们已经很熟悉，关键是第二行：

```bash
nohup .venv/bin/fastapi run > backend.log 2>&1 &
```

一句话四个零件，逐个拆：

- **末尾的 `&`**——把这条命令**丢到后台**跑，终端不用干等着；
- **开头的 `nohup`**——"**no hang up**"，别挂断。它让这个进程**不再随着 SSH 断开而被杀掉**。光有 `&` 还不够：`&` 只是不占着终端，人一走它照样陪葬；
- **`> backend.log`**——把输出**重定向**进一个文件。以前日志直接打在终端上，现在没终端可打了，不接住就全丢了；
- **`2>&1`**——认个脸：把**错误输出**也一并塞进同一个文件。（`1` 是正常输出，`2` 是错误输出，这句的意思是"2 号跟着 1 号走"。）报错和正常日志混在一处，翻起来方便。

敲完回车，屏幕上会蹦出一个数字——**那是进程号（PID）**。

> 顺带留意这次写的是 **`.venv/bin/fastapi` 这个完整路径**，而不是先激活环境再跑 `fastapi`。因为丢到后台的进程不见得还带着我们 activate 出来的那套环境——**指名道姓，最保险**。

现在再来一遍那个实验：**关掉 SSH 窗口，再次访问我们的网站**，这一次应该就可以正常访问了。

## 思考：现在部署方式好不好

站点上线了，全世界能访问。但**它是用最朴素的办法凑出来的**，存在一些缺点

**第一：后端服务脆弱**。 `nohup` 确实让后端活过了 SSH 断开，但它只解决了这一件事，还有一些问题它没解决：

- **服务器重启，它不会自己起来**。服务器毕竟也是一台电脑，虽然它以稳定运行作为主要特征，但仍然还是会有关机重启的可能——云厂商维护、断电、我们操作的时候手滑重启，一旦发生这些事情，网站后端服务就悄无声息地没了；
- **它崩了也不会自己起来**。如果代码里有个 bug 把进程弄死了，就会一直死着，直到我们发现为止；
- **管起来全靠手工**。比如说我们更新了代码，想停掉它重启一次，会是一件比较麻烦的事情（得去找到进程号）。我们甚至想看它现在还是不是活着，都是一件比较麻烦的事儿。
- 想看日志也比较麻烦，得自己记着日志文件在哪儿。

**第二：裸奔的8000端口。** 8000 这个端口现在**一直对公网开着**，而且是个**裸端口**：

- **这个端口没有日志**：谁来访问过8000端口、干了什么，无从查起（80端口就有，Nginx 会记录）；
- **这个端口没有加密**：内容明文来回跑。下一节我们要给网站上 HTTPS，而 HTTPS 是配在 Nginx 上的——**走 8000 的那些请求，一个字都保护不到**；
- **这个端口没有任何管控**：限流、转发规则，一概没有。

多开一扇门，就多一分风险，这也是为什么服务器的防火墙不会默认开那么多端口的原因。

**第三：前后端跨源。** 浏览器的CORS策略对于前后端有太多的限制，虽然我们在开发阶段已经逐个把我们遇到的问题解决了，但是后续我们要上域名、上HTTPS的时候，这些跨源问题还会持续困扰我们。我们是否能在部署环节让前后端变成同源的呢？


这三个问题，就是我们下一节要做的事情：

- **systemd** 取代 `nohup`——开机自启、崩溃自愈、一句命令问状态、一句命令看日志；
- **Nginx 反向代理**把 `/api/` 接进 80 端口，**8000 端口不再对外提供服务**；
- 前后端都使用80端口之后，就自然变成了**同源**，配置文件也就更简单了。

下一节，我们就把这套朴素做法一样样换掉。
